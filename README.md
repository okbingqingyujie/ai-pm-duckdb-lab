# AI 客服转人工成功率 77.8%，到底算了哪些会话？

AI 产品经理精选 · 2026-11-24 · 开源项目与指标评审

**收到“已转人工”的消息、排进队列、真人实际接手，是三个事件。** 如果新版才开始记录第三个事件，仪表盘上的百分比可能变了，但你还不知道用户的等待体验有没有变好。

这是一份独立原创学习笔记，不是 DuckDB 官方教程、完整源码或线上复盘。案例、数据和门槛均为虚构；SQL 未在 DuckDB 中运行，也没有连接客服系统或采集真实会话。

## 为什么选 DuckDB

[DuckDB](https://github.com/duckdb/duckdb) 是分析型数据库，适合拿小样本做指标口径核对。2026-11-24 北京时间核查，[GitHub API](https://api.github.com/repos/duckdb/duckdb) 显示 **43,287 Stars**，仓库公开、未归档且当日仍有推送。它不是新项目；[v2.0.1](https://github.com/duckdb/duckdb/releases/tag/v2.0.1) 于 2026-11-20 发布，是近期的修复版本，不是按列名合并功能的首次发布。已核对该版本的 [README](https://github.com/duckdb/duckdb/blob/v2.0.1/README.md) 和 [MIT 许可证](https://github.com/duckdb/duckdb/blob/v2.0.1/LICENSE)。

这里用两条 SQL 规则：[UNION ALL BY NAME](https://duckdb.org/docs/2.0/sql/query_syntax/setops) 按列名合并，缺列补 NULL，保留重复行；[COUNT(*)、COUNT(字段) 与 COUNTIF](https://duckdb.org/docs/2.0/sql/functions/aggregates) 分别计全部行、非空行和真值行。SQL 可以把表拼起来，但不能告诉你一个空值是旧版没采集，还是新版漏采。

## 先把指标写清楚

场景：客服产品经理想决定，是否要扩大 AI 转人工流程的试点。练习只覆盖人工服务开放时段，统计单位是一次符合条件的转接请求，按请求 ID 去重。以请求首次进入转接流程为起点，目标是**同一工单被有权限的真人客服在 10 分钟内接手**。从这一刻起计时，不因重试而重置窗口。入队、AI 文案和机器人自动分配不算接手；“接手”也不等于问题解决。

| 记录版本 | 符合条件 | 已知成功 | 已知未成功 | 未知 |
| --- | ---: | ---: | ---: | ---: |
| v1，仅记录转接请求 | 100 | 未测 | 未测 | 100 |
| v2，开始记录真人接手结果 | 100 | 70 | 20 | 10 |

新版的 20 次未成功，是通过完整的客服系统记录确认在窗口内未接手；10 次未知是数据缺失或冲突未解决。没有记录，不能当作没接手。只汇报 **70/90 = 77.8%** 会让人误以为这是新版所有请求的成功率。新版覆盖 **90/100 = 90%**，两版合计覆盖 **90/200 = 45%**。假设已知记录准确，仅把 10 个未知分别当作全失败和全成功，新版全量成功率可界定为 **70%–80%**；这是可能范围，不是置信区间。旧版没有可比成功率，不能做 0% 对 77.8% 的提升结论。

## 纸面练习：重画这个看板

先手算，再用下面的只读 SQL 对照。输入模拟已经按请求归并、已过观察窗口的摘要，一行对应一次请求。它不替代实际事件去重和对账。

```sql
WITH v1 AS (
    SELECT 'legacy-' || i::VARCHAR AS request_id, 1 AS schema_version
    FROM range(1, 101) AS r(i)
), v2 AS (
    SELECT 'current-' || i::VARCHAR AS request_id, 2 AS schema_version,
           CASE WHEN i <= 70 THEN TRUE WHEN i <= 90 THEN FALSE END
               AS human_accepted_in_10m
    FROM range(1, 101) AS r(i)
), requests AS (
    SELECT * FROM v1
    UNION ALL BY NAME
    SELECT * FROM v2
)
SELECT schema_version,
       count(*) AS eligible,
       count(human_accepted_in_10m) AS observed,
       countif(human_accepted_in_10m) AS confirmed_success,
       count(*) - count(human_accepted_in_10m) AS unknown
FROM requests
GROUP BY schema_version
ORDER BY schema_version;
```

预期依次为 `(1, 100, 0, 0, 100)` 和 `(2, 100, 90, 70, 10)`。第一行的 0 是确认成功的**可观测记录数**；界面成功率应显示“不支持测量”，不能显示 0%。

## 怎么拿去做需求评审

- **MVP 先补对账，再扩大试点。** 指标从符合条件的请求台账出发，左连接已对账的结果。看板同时列出时间窗、符合条件数、已知成功数、覆盖率和未知原因。样本中旧版无可比基线，不能据此宣布新版改善；必要时在两组使用同一条权威客服记录并先做小流量校验。
- **把边界写进验收。** 同一个接手事件重放两次，分子分母都不变；当前版缺一条结果，仍留在分母且标为未知；超过 10 分钟的可靠接手记录在本指标下不算成功；错工单的事件不能算成功；同一请求出现未能对账的矛盾结果时只记一次未知，并单列冲突。所有用例都通过且每版“成功 + 未成功 + 未知 = 符合条件”后，再把看板用于决策。
- **覆盖够了也不代表公平可比。** 示例可要求两臂覆盖均不低于 95%，同时检查缺失是否集中在高峰、渠道或语言。如果新功能改变了谁会发起转接，不能用事后发起转接的两组推断整体用户因果效果；需要以曝光前已定义的合格人群为基础另设指标。观察窗口和覆盖阈值是练习设定，不是行业标准。
- **控制范围。** 此法适合埋点升级、历史数据拼表和灰度看板验收，不适合用来推断满意度、人员负载或问题解决率。为核对指标只需最少的请求、工单关联标识和时间；练习不要上传真实对话、客户姓名或手机号。

**面试怎么说：**“我会先问这 77.8% 的分母是谁。旧版不记录真人接手，新版还有 10% 结果缺失，我会先把覆盖率和未知原因放上看板，在两组都能用同一口径观测后再判断要不要扩量。”
